## Correcciones de esta rama

- Status extraído a lectores sin métodos de ejecución; CLI no inicializa el provider/principal para inspeccionar. Conserva la proyección y sólo recupera cierres desde resultados durables.
- Superficie operativa tipada `orgctl code-runner mission request-review` / `review`. Usa el servicio existente, no inventa checks ni salta la validación de workspace, gates o identidad del reviewer. No tiene operación apply, push o merge. No hay aprobación por defecto.
- La propuesta de implementación recibe la allowlist, denylist y los cuatro gates desde las mismas estructuras que impone missionplan. El prompt no concede permisos.
- Se explicita la frontera epistemológica del revisor: no inferir defectos por tamaño/solapamiento ni inventar rangos. No se amplía egress y no se cambia ningún validador para aceptar afirmaciones sin evidencia.

## Secuencia operativa después de un candidato real

Sólo con IDs obtenidos de evidencia durable, no inventados:

```sh
orgctl code-runner mission request-review --task TASK_ID --workspace WORKSPACE_ID --actor-role ingenieria_ia/code-runner --json
orgctl code-runner mission review --promotion PROMOTION_ID --requirement REVIEW_REQUIREMENT_ID --actor-role REVIEWER_AUTORIZADO --verdict APPROVE --reason-code independent_review --reason 'Conclusión de una revisión real del candidato y sus gates' --json
```

La segunda operación exige revisión efectiva previa; nunca ejecutarla sólo para desbloquear un smoke. `REMEDIATE` y `BLOCK` siguen disponibles. El actor debe estar autorizado por staging/canonical; la CLI no concede esa autoridad. Una promoción staging aprobada no equivale a merge en GitHub.
